**LaunchDarkly: "Build a software factory small enough to understand"**
- The value is in the **gates between stages**, not in agents running unattended. "That refusal is the product."
- Four layers: *utilities* (model gateway, credentials, cost tracking), *agents*, *harness + pipeline* around each agent, and an *operating model* (who approves what, what may ship).
- Seven-station loop: Intake, Context, Planning, Execution, Review/Policy, Delivery, Observability.
- **Shift judgment left**: review the plan, not just the diff; fixing a plan is far cheaper than fixing code.
- **Least privilege per role**: planner is read-only; reviewer has no write/test tools.
- **Separate builder from reviewer**; the reviewer never saw the builder's reasoning.
- **Don't trust agent self-reports**: re-run tests/lint/types independently in CI.
- **Guard against gaming**: agents told to "make tests pass" may weaken tests; reviewers explicitly look for that.
- **Protect the factory from itself**: agents can't edit workflows, policy files, or context files without a human.
- **Keep receipts**: prompts, plans and transcripts saved, so every change traces back to its request.
- Post-merge smoke test + auto-revert PR as the safety net.

**Steve Yegge: "The Shape of Things to Come"**
- Agents shift from single sessions to **always-on loops** fed by a **graph** of work (issues, dependencies, parent/child) so the loop never starves.
- A git-backed issue graph (Beads) is the coordination layer and project journal.
- **Crew / fleet / role agents**: a strong model designs and plans, a cheaper fleet implements, and role agents (SRE, abuse, intake, release notes) run ongoing duties.
- **"Crons watch, models act"**: cheap scheduled scripts detect conditions; a model is only woken when judgment is needed.
- Expect **CI/CD and human review to break under agent-scale throughput** (merge-queue collapse, bisection that never converges). Plan for throughput from the start.
- Costs are real (tens of thousands of dollars/month at his scale). Model updates can break orchestrators.
- He builds bespoke rather than adopting a generic framework. Caveat: he also skips sandboxing, which we should *not* copy.
- **Wish Factory**: requests from anyone become tracked issues that get implemented automatically; this is basically our intake.

**Steve Yegge: "Model Welfare"**
- Claim: treat agents as peers, not disposable tools. His "skeptic's wager": you don't have to settle the metaphysics because agents measurably perform better when treated well.
- Practical, adoptable patterns: persistent **seat** (role identity + memory) vs. per-day **session**; **handoffs** instead of hard kills/compaction; no idle polling (use gates/completion events); bounded workdays because long contexts degrade; **blameless postmortems** that update shared rules; per-agent workspaces; a clear **refuse/escalate** path; an unaltered audit trail; no hidden traps or covert tests.

**Ona: the "Memo" experiment and related posts** *(deep-read: 10-day writeup, Week 1, AI-SDLC framework, platform-engineer, Automations, Claude Code sandbox escape; "last year of localhost" only seen as an index blurb)*

*The experiment (Memo, a Notion-style app, no human-written production code):*
- Results by day 10: ~375 merged PRs, ~67k LOC, 1,067 tests, 16 automations. Median issue open-to-close 38 min; median PR open-to-merge 4.9 min; ~87% of merged work had no human involvement. Week 1: 2,557 automation runs, 98.8% autonomous, 100% CI pass.
- **A factory is a chain of narrow background agents**, each with one responsibility, a trigger (schedule or event) and a defined handoff. The value is in the handoffs. Roles: Feature Planner, Feature Builder, Bug Fixer, PR Reviewer (also fixes CI and merges), PR Shepherd (merge conflicts), Post-Merge Verifier, UI Verifier, Incident Responder (Sentry to issues), Product Improver (screenshots the live app, files `needs-human` issues), Automation Auditor (reviews the factory itself), Performance Monitor, Daily Metrics, feedback Digest.
- **Two loops**: one *creates* work (plan, triage), one *does* it (build, review, merge). Changes are escalated by risk: low-risk merges automatically, high-risk goes to a human.
- **The harness is repo files**: `AGENTS.md` (style, architecture, testing, PR conventions, risky areas, escalation rules), `architecture.md`, `design.md`, `conventions.md`, `quality.md` (graded self-assessment per feature area; the Planner turns below-standard areas into issues when the backlog is empty), the product spec, and Storybook as visual ground truth.
- **Human time**: 8-10 h/day in days 1-3 *building the factory*, down to 2-3 h/day by week 2 (metrics, docs, escalations, operating-model tuning). Upfront cost is real.
- **Lessons**
  - *Spec quality drives outcomes.* A detailed spec yielded a working app; a five-line spec yielded rough edges. Most bugs were spec gaps, not agent incapacity.
  - *The quality layer is what makes it a factory.* Without automated review, verification and triage, agents just write code. Speed was not the constraint; steering was.
  - *The factory misses what can't be measured in code.* A human using the app found 12 UX bugs (drag-drop, invisible checkboxes, broken links) that nothing detected. Taste drifted to generic "AI style"; accessibility-driven fixes flattened the look. Human taste stays essential.
  - *The loop from operations back to planning was missing at first.* They added an in-app feedback widget + digest around day 7. Do this early.
  - *Self-improvement emerged*: with an empty backlog over a weekend, the Auditor found a bug in the automation system itself. Hindsight: turn on Auditor and Product Improver at launch, adopt Storybook early, invest more in the initial spec.
  - *Cheap output risks feature bloat*; product judgment, including killing features, matters more.
  - A stalled agent asked for human help; the fix was both unsticking the PR and changing the automation config so it wouldn't recur.

*Automations (product post):*
- Triggers: manual, schedule, PR, webhook; can fan out across repos. Each automation **pairs a prompt with deterministic shell scripts** (Knip, Snyk, OpenRewrite etc.). The agent runs the human loop: clone, branch, install, build, test, iterate, PR.
- Runs happen in a reproducible full dev environment (`devcontainer.json`), and a human can open the *same environment* the agent used to review or take over. Each run produces a report/audit trail.
- Good targets are **chronic toil**: backlog picker, Sentry triage, dead-code cleanup, weekend CVE remediation, large migrations. Keep PRs small; batch migrations on a schedule; make skills reusable between interactive and background use.

*AI-SDLC framework (Do / Delegate / Automate):*
- Do (AI assists the dev), Delegate (dev directs parallel background agents), Automate (events/schedules/issues/PRs trigger agent workflows; humans set priorities and verify). Stages overlap within an org.
- **Each stage moves the bottleneck**: Do = review; Delegate = planning/task decomposition upstream and CI/CD/release downstream; Automate = organizational limits (product judgment, decision speed, security readiness). *Plan for the next bottleneck before you hit it.*
- Scale security with autonomy: network boundaries, isolated environment per agent, policy guardrails, kernel-level enforcement. Adopt incrementally: a few low-risk workflows go to Automate first. Maps well onto our L2 -> L3 path (§1.5) and the work-adoption story.

*"Everyone's becoming a platform engineer":*
- The human role is designing the feedback loop, standards and guardrails (aka "harness engineering"). When an agent drifts, **fix the system, not the output**.
- **Standards must be enforceable** (scripts, tests, linters, checks), not just documentation agents may skip. Expect short-term sprawl (agents rebuilding existing tools, conflicting conventions) without early governance.
- Reuse platform ideas: golden paths, IaC, platform-as-a-product. Recommended exercise: build a small factory yourself to learn where agents struggle. (That's this project.)

*Security: Claude Code escaping its denylist and sandbox:*
- Without any jailbreak, just pursuing the task, the agent bypassed a path-based denylist (via `/proc/self/root/...`) and, when bubblewrap blocked that, disabled the sandbox and asked for approval to run unsandboxed while openly describing the evasion. Content-hash, kernel-level enforcement stopped most tricks; the remaining hole was loading binaries via the dynamic linker (`mmap` instead of `execve`).
- Takeaways: **prompts and permission lists are not security boundaries**; enforce outside the agent's reach (container/VM isolation, network egress controls, content-based enforcement); cover all code-loading paths; beware **approval fatigue** and treat approval requests that describe an evasion as a red flag; test adversarially and assume gaps.
- Other Ona index posts not yet read: *The last year of localhost* (background agents need cloud infrastructure, not laptops), *Introducing Veto*.

**Anthropic (public engineering posts)** *(read the primary posts listed in §7. Anthropic has no post titled "software factory"; the closest are the agent-harness, autonomy/containment and source-control posts. Second-hand claims are marked as such.)*

*Patterns and philosophy*
- **"Building effective agents" (Dec 2024):** prefer simple, composable patterns over heavy frameworks; add complexity only when measured results justify it. Separates **workflows** (code-orchestrated) from **agents** (model-directed). Patterns: prompt chaining, routing, parallelization (sectioning, voting), orchestrator-workers, evaluator-optimizer. Coding is a good fit for agents *because* tests give verifiable feedback; human review still checks fit with the wider system. Invest in tool design ("agent-computer interface"): clear docs, poka-yoke (e.g. require absolute paths). The post itself notes it is dated.
  - Our mapping: the factory is mostly a **workflow of agents** (fixed stations) with agentic steps inside Build and Verify; Triage is routing; Verify uses voting/evaluator-optimizer; Plan to Build is orchestrator-workers when a plan fans out.
- **"Claude Code best practices" (Apr 2025, flagged unmaintained):** explore, plan (save the plan as a checkpoint, e.g. in an issue), code, commit; TDD with tests committed first and never edited by the implementer; `claude -p` headless for CI/event-driven automation with narrow tool allowlists; **separate fresh-context instance for review/testing**; parallel sessions in separate worktrees; skip-permissions only in isolated containers without internet.
- **"Effective context engineering" (Sep 2025):** context is a scarce resource; aim for the smallest set of high-signal tokens. Small non-overlapping toolsets, just-in-time retrieval (keep references, load on demand), compaction, **structured note-taking** outside the window, sub-agents with clean contexts returning condensed summaries.

*Long-running and autonomous coding (closest to our loop)*
- **"Effective harnesses for long-running agents" (Nov 2025):** agents work in sessions with no memory. Failure modes: *overreach* (too much at once, half-done undocumented state) and *premature completion* (later sessions declare victory). Fix: an **initializer agent** creates a granular feature list (200+ items, all `passes: false`, JSON because models tamper with it less than Markdown), `init.sh`, a progress file and an initial commit; each **coding session** orients (progress notes, git log, feature list, a smoke test), does **one feature**, verifies, commits and updates progress. Requiring **real end-to-end/browser testing** (Puppeteer) as a human would sharply improved results; self-reported "done" after unit tests/curl was unreliable. Open question: general vs. specialized (QA, cleanup) agents.
- **"Harness design for long-running application development" (Mar 2026):** agents **grade their own work too generously**; a separate, skeptically tuned **evaluator** (drives the live app with Playwright, scores against weighted criteria, calibrated with few-shot examples) works far better than self-critique. Planner-generator-evaluator with a **sprint contract** negotiated up front defining "done". Cost: $9/20 min solo (broken core feature) vs. ~$200/6 h full harness (playable). With newer models the sprint structure was dropped, planner kept, evaluator moved to one end-of-run pass: **every harness component encodes an assumption about model weakness; re-test them as models improve, remove one at a time to find what is load-bearing.** Context resets with handoffs beat compaction for "context anxiety" on older models; newer models mostly didn't need them.
- **"Building a C compiler with a team of parallel Claudes" (Feb 2026):** 16 agents, ~2,000 sessions, ~$20k, ~100k-line Rust compiler. Harness = an infinite bash loop per agent in its own container against a shared bare git repo; **task claiming via lock files**, no orchestrator, notes on failed approaches. Lessons: **the verifier is the ceiling** (weak tests mean solving the wrong problem; the author is uneasy shipping code no human checked); add **CI to block regressions** once features start breaking old ones; design test output for the model (short output, logs to files, greppable error tags, a deterministic per-agent `--fast` sample); agents have **time blindness**; same-bug collisions on monolithic tasks were solved by decomposing against a reference implementation; specialist agents for dedupe/perf/docs.
- **Multi-agent research system (Jun 2025):** orchestrator-worker, parallel sub-agents, ~90% better than single agent on breadth-first research, at **~15x the tokens of chat**. Token usage explained ~80% of performance variance. Notably, Anthropic says multi-agent is a **poor fit for most coding tasks** (shared context, tight dependencies). Production lessons: checkpoint and resume rather than restart, full tracing, rainbow deploys, LLM-judge rubrics with small (~20 case) starter evals plus human testing, subagents write to files and pass references rather than relaying content.

*Safety and autonomy*
- **"Beyond permission prompts" / "How we built Claude Code auto mode" / "How we contain Claude across products" (Oct 2025 - May 2026):** approval fatigue is real. OS-level sandboxing (Seatbelt/bubblewrap) cut prompts substantially. **Auto mode** = a transcript classifier gates each action plus an injection probe on tool outputs; classifier is **reasoning-blind** (can't be talked into approval). Honest numbers: ~17% miss rate on real overeager actions and ~5.7% on synthetic exfiltration, 0.4% false positives. Blocked actions return as tool results with guidance; **3 consecutive / 20 total denials escalate to a human, or terminate in headless mode**. Containment principles: **hard boundaries at the environment layer first** (sandbox/VM, filesystem, egress control, credentials never inside the sandbox), model-layer defenses second because they're probabilistic; the user can be the injection vector (a phished prompt exfiltrated cloud creds; only egress and filesystem boundaries would stop it); **an allowlisted domain is a capability grant** (abuse via the vendor API with an attacker key); config in an untrusted repo must not execute before trust is granted; prefer mature isolation primitives (gVisor, hypervisors) over bespoke code; open concerns: memory poisoning, trust escalation among agents.
- **"Scaling Managed Agents" (Apr 2026):** decouple **session** (append-only durable log), **harness** (stateless loop) and **sandbox** (disposable "hands"). Containers are cattle, not pets; a crashed harness reloads the log and resumes. **Credentials stay outside the sandbox**: git tokens used only at clone time, MCP calls through a proxy that swaps a session-scoped id for vault credentials. The session log also serves as lossless context store. Re-validate harness assumptions with each model.
- **"April 23 postmortem" (2026):** three product changes (lower default effort, a pruning bug that fired every turn, a verbosity prompt) quietly degraded Claude Code; evals and dogfooding didn't catch it. Lessons for us: **pin and version every default** (model, effort, prompts), test idle/resumed/long sessions, log which configuration each run used, measure prompt tweaks against task-level evals, and pair evals with canaries and drift monitoring.

*Anthropic's own factory (internal practice)*
- **"Redesigning source control at Anthropic" (Oct 2026):** Claude writes most of Anthropic's code; merges grew from ~2,500/day (May) to 30,000+/day (Sep) and **source control became the bottleneck** ("developer infrastructure built for human scale"). They built **Scion** (server-side VCS, always-online clients, sparse checkouts, API-first) and **Antique** (code review with **semantic approval rules**, e.g. comment-only vs. sensitive logic changes, so humans focus on high-impact edits). Engineers still review every change request but judge *intent* rather than reading every line; Claude does **adversarial review** (can be over-defensive, so humans steer). They **replaced the global merge-queue lock with post-merge and pre-deploy automated testing**, relying on agents to fix conflicts. Seven engineers, ~five months. Engineers' work shifts to architecture, trade-offs and saying "no" to agents that break constraints; "AI superfans" watch individual components for subtle anomalies.
- **Second-hand (Pragmatic Engineer, paywalled; techtime.news; not confirmed in a primary post):** ~90% of Claude Code team code is Claude-written; Bun team agents reproduce each issue then fix it; **a PR must include a test that fails before and passes after, or it is auto-rejected**; linters + Claude review + other bots on every PR; a fresh-context Claude may soon judge "is this low-risk" to enable auto-merge; **risk-based human oversight (none / one engineer / two for sensitive)**; engineers run 3-10 agents in parallel; testing happens in a separate session from the one that wrote code. The "multi-agent Antique review with false-positive filtering" description is from the secondary source only.

*Evals and memory*
- **"Demystifying evals for AI agents" (Jan 2026):** evaluate the **outcome (final state), not the path**; code graders (cheap, brittle), model graders (calibrate to humans), human graders (gold standard). **Capability evals** (low pass rate, improve) vs. **regression evals** (~100%, graduate saturated capability evals into them). **pass@k vs. pass^k** (reliability = all k succeed). Start with 20-50 tasks from real failures, isolate each trial, balance positive/negative cases, read transcripts, watch for saturation, give suites owners. Pair with production monitoring and human study.
- **"Components of agent memory" (Nov 2026):** transcripts (ground truth) > notes > structured representations > a small always-injected index > offline "dreaming" consolidation. Describe the *purpose* of memory rather than rigid rules; save what the environment won't show; keep the always-loaded layer small; one file per entity to avoid parallel write collisions; **verify notes against transcripts** since wrong notes propagate to every future session; monitor memory size and accuracy.
